# ADR 0027: Redacted Item Access and Per-Field Secret Release

## Status
Accepted. Amends [ADR 0003](0003-omawarden-rust-native-helper-and-daemon-architecture.md) (what the daemon returns), [ADR 0010](0010-daemon-session-token-and-access-control.md) (caller checks, idle timer) and [ADR 0025](0025-quick-unlock-with-system-authentication.md) (suspend handling). The wire contract is in [contracts.md section 3](../agents/contracts.md#3-daemon-item-access-contract-adr-0027).

## Context
A security review of the resident daemon found:

1. `list`, `search` and `get_item` returned every decrypted item, with passwords, TOTP seeds, card numbers and codes, identity document numbers, notes, hidden custom fields and password history, to any process of the same user. The only gate was "is the vault unlocked". The overlay (a long-running, unsandboxed Quickshell process) therefore held the whole plaintext vault and copied by sending plaintext back to the engine.
2. Caller verification was the UID alone, so `socat` could talk to the daemon, and a same-user process could stop a locked daemon and listen on its socket for the next master password.
3. Requests were read without a size cap or timeout, with one thread per connection and no limit.
4. A client could send `"touch": true` to reset the idle timer, and `set_auto_lock 0` disabled the idle lock.
5. Suspend was detected by polling `busctl` every 2 seconds, without an inhibitor, so the key could still be in RAM when the machine slept. The daemon detached with `setsid` and could outlive the desktop session.
6. Decrypted item strings, the raw user key, the decrypted RSA private key DER and the master password (in the CLI and in the unlock request) were not zeroized.
7. The lock hook embedded the helper path in a bash script unquoted, and the runtime directory fell back to `/tmp` without race-safe checks.

Quick unlock was reported as on by default; that part was stale: `quick_unlock` already defaulted to `false` and a soft lock already hard-locked when it was off. This ADR keeps that behaviour and adds a regression test for it.

## Decision

### 1. Redacted reads
`list`, `search` and `get_item` return a redacted view built from an allowlist (`item_redaction.rs`): only keys named in a per-section policy are copied, so a field added to the decrypted model later stays private until it is deliberately published. Each withheld secret becomes a `has_<field>` flag; cards keep `number_last_four`, but only when the number has at least 12 digits (a shorter "number" would be revealed whole). Custom field values are published only for text (0) and boolean (2) fields; hidden (1) and any unknown type are treated as secret. A field whose type is missing or not an integer is recorded and reported as hidden (1) when it is decrypted, so a malformed field fails closed instead of being published as text.

Search no longer matches secret content. The internal search text excludes notes, card numbers and codes, identity document numbers and hidden field values, and `search` no longer scans notes. Otherwise a redacted API would still be an oracle: repeated searches could recover a secret one character at a time. Searching inside secure notes is the feature this costs.

### 2. Per-field release with a budget
A secret leaves the daemon only through `reveal_field {id, field}` or `copy_field {id, field}` (`secret_access.rs`), with the field identifiers of contracts.md 3.3. `login.totp` releases the current code and the seconds remaining, never the seed. `copy_field` copies inside the daemon through the existing clipboard module (`wl-copy --sensitive` over stdin, auto-clear always scheduled) and does not return the value. `wl-copy` is taken only from `/usr/bin/wl-copy` or `/usr/local/bin/wl-copy`, and only when the file is owned by root and not writable by group or others, the same rule as `pkcheck`; it is never looked up in `PATH`, where a same-user process could plant a program that receives every copied secret. The existing `copy` action remains for caller-supplied, non-secret text (usernames, URIs, generated passwords with the sensitive hint). The `totp` action keeps generating codes from a caller-supplied seed but refuses item lookups, which now go through `reveal_field`.

Releases are counted in two sliding windows: at most 30 in 60 seconds (`MAX_SECRET_RELEASES_PER_WINDOW`, `SECRET_RELEASE_WINDOW`) and at most 120 in one hour (`MAX_SECRET_RELEASES_PER_HOUR`, `SECRET_RELEASE_HOURLY_WINDOW`). A request whose releases would exceed either limit is refused, the vault is hard-locked and a warning is logged. `password_history` is charged one release per history entry (at least one), because one request returns every entry; a history longer than 30 entries can therefore never be released and locks the vault. Bulk extraction through the per-field API costs one request per secret and ends after 30, and the user notices the lock. The hourly window closes the paced variant: 30 releases every 60 seconds never trip the short window, but trip the hourly one after four minutes. Releases do not reset the idle timer (section 5), so paced extraction cannot also keep the vault unlocked. CLI commands that print or copy secrets (`totp`, `copy <query>`, `vault reveal`, `vault copy-field`) go through the same two actions and the same budget.

### 3. Caller verification in both directions
Both the daemon and the CLI read the peer's credentials with `SO_PEERCRED`, require the same UID, and compare `/proc/<pid>/exe` with their own executable, after stripping the kernel's ` (deleted)` marker (a package upgrade unlinks the running binary) and resolving symlinks (`peer_identity.rs`). The daemon refuses a foreign client; the CLI refuses to send anything, the master password included, to a daemon that fails the check. A new daemon also refuses to start while another daemon is still serving the socket, instead of deleting the live socket and taking its place.

**Kernel limitation.** Linux only exposes `/proc/<pid>/exe` of a *dumpable* process to an unprivileged peer. Every omawarden process makes itself non-dumpable at startup (ADR 0009), so for a genuine peer the read fails with `EACCES`. The check therefore accepts a peer whose link is concealed and rejects a peer whose link is visible and names another program. This stops ordinary programs (`socat`, shells, Python, Node, curl): verified on this machine, a Python client is refused with "peer executable '/usr/bin/python3.14' is not '…/omawarden'". A same-user program that calls `prctl(PR_SET_DUMPABLE, 0)` first, or that starts the real binary with `LD_PRELOAD` or under its own ptrace, is not stopped; no unprivileged mechanism can attest the executable of a non-dumpable process. Making omawarden dumpable again to enable the check would expose its memory to the same users this is meant to keep out, so that trade is refused. Stronger isolation needs an LSM or sandbox around untrusted applications.

### 4. Request bounds
`daemon_requests.rs`: each connection carries one request line of at most 64 KiB, which must arrive in full within 5 seconds. The 5 seconds are a total deadline for the request: each read is limited to the time that remains, so a client that trickles one byte every few seconds loses its slot after 5 seconds instead of holding it for hours. The response has a 5-second write timeout; at most 16 connections are served at once and further ones are refused with an error. The request is read straight into one zeroizing buffer allocated at its final size (64 KiB + 1), with no intermediate reader buffer and no reallocation, so the unlock request (which carries the master password) leaves no unzeroized copy behind.

### 5. Idle timer and auto-lock range
The action table (`daemon_actions.rs`) states per action whether it needs an unlocked vault and whether it resets the idle timer. User activity is browsing the unlocked vault (`search`, `get_item`) and a successful unlock or quick unlock; nothing else resets the timer. In particular:

- `reveal_field` and `copy_field` do not, so a caller releasing secrets at a steady pace (within the budget) cannot also keep the vault unlocked; the idle lock ends such a session.
- `copy` and `generate_password` do not: they work while the vault is locked, so periodic calls would otherwise keep the idle timer of the next session fresh without needing any key.
- `list` (the overlay loads it after every unlock), `sync` (run in the background after unlock), `totp` (seed supplied by the caller) and all polling do not. The `"touch"` field is gone. `set_auto_lock` accepts 60 seconds to 12 hours and refuses zero; `config set --auto-lock` validates the same range, and an out-of-range configured value starts the daemon with 15 minutes and a warning. The 12-hour session ceiling is unchanged.

### 6. Suspend: delay inhibitor and PrepareForSleep
While key material is resident (vault unlocked, or a key retained by a quick-unlock soft lock), the daemon holds a logind delay inhibitor: `systemd-inhibit --what=sleep --mode=delay --who=omawarden --why=… /usr/bin/cat`, with `cat` waiting on a pipe from the daemon. Closing the pipe ends `cat`, which ends `systemd-inhibit` and releases the inhibitor; if the daemon dies, the pipe closes and the inhibitor goes with it. A `dbus-monitor --system` child with a match rule for `org.freedesktop.login1.Manager.PrepareForSleep` delivers the signal as it happens (no polling). On `PrepareForSleep(true)` the daemon hard-locks (zeroizing keys, plaintext and the retained key), withdraws its own clipboard offers (section 11) and releases the inhibitor, and the suspend proceeds. An unlock whose key derivation is still running when the signal arrives ends locked: every lock taken for a suspend (the signal, the polled `PreparingForSleep` fallback and the BOOTTIME drift detector) bumps a sleep generation first, an unlock samples it before deriving the key and hard-locks again, with an error, if it changed. From `PrepareForSleep(true)` until `PrepareForSleep(false)`, no unlock can complete; a detected resume or a restart of the monitor also ends that state, so a missed `false` signal cannot block unlocking. The monitor runs from daemon start, receives `SIGKILL` if the daemon dies (`PR_SET_PDEATHSIG`), and is restarted by the watchdog if it exits. All programs are resolved from fixed, root-owned paths, like `pkcheck`. No root is needed; delay inhibitors and signal eavesdropping are available to the user.

On this machine `InhibitDelayMaxUSec` is 15 s (`/etc/systemd/logind.conf.d/20-inhibit-delay.conf`, `InhibitDelayMaxSec=15`; the logind default is 5 s). The lock is an in-memory purge plus a signal to each `wl-copy` this daemon still serves, and releasing the inhibitor is bounded at 500 ms; the regression test asserts that lock and release complete well inside 5 s. The 2-second `PreparingForSleep` poll and the BOOTTIME drift watchdog remain as fallbacks when the monitor or the inhibitor is unavailable.

### 7. Session end and termination signals
At startup the daemon records `XDG_SESSION_ID` and, if it exists, the Wayland socket `$XDG_RUNTIME_DIR/$WAYLAND_DISPLAY`. Each watchdog tick (2 s unlocked, 5 s locked) it asks logind for the session `State` (`loginctl show-session <id> --property=State --value`); when logind reports `closing` or "No session", or the compositor socket has disappeared, the daemon hard-locks, removes its socket and exits. A failed query that is not "No session" is never treated as an end. On this machine the overlay runs inside `wayland-wm@hyprland.desktop.service`, so the daemon it spawns already inherits that unit's cgroup; the session check covers a daemon started from anywhere else, such as a terminal. Verified on this machine: the session reports `State=active`, `Type=wayland`; with the Wayland socket removed the daemon exited within one tick, and with a session id logind does not know it exited after its first tick. SIGTERM, SIGINT and SIGHUP are handled through a self-pipe and hard-lock before exit.

### 8. Zeroization
- `VaultItem` zeroizes every string it owns, including the decrypted `serde_json::Value` sections (`secret_memory::zeroize_json_value`), on drop, so the cache, the clones handed to handlers and search results are all scrubbed on lock, purge and sync replacement.
- Decryption moves decrypted strings into `Value::String` instead of `json!`, which would serialize a copy and drop the original unscrubbed.
- The raw user key bytes (unlock and login), the decrypted RSA private key DER, and the probes that validate a retained quick-unlock key are wrapped in `Zeroizing`.
- AES-CBC decryption works in place on a `Zeroizing` copy of the ciphertext; a failed decryption zeroizes it, and a successful one truncates it to the plaintext and returns that buffer instead of copying the plaintext out of it.
- A sync decrypts with a copy of the user key instead of holding the key lock, and stores its items only if the vault has not locked since the sync sampled the lock generation; the check runs under the same items lock under which a lock bumps the generation and clears the items. A lock landing during a sync can therefore never be followed by the sync writing plaintext back.
- The CLI reads the master password into `Zeroizing<String>` (prompt and stdin, including the JSON login payload, which is zeroized after parsing) and sends it through `send_unlock_request`, which zeroizes the request value. `send_daemon_request` zeroizes its copy of every request and the serialized line. The daemon zeroizes the request buffer and the parsed request after dispatch, and every response (which may carry a released secret) after writing it.
- Residual: serde's internal scratch buffers for escaped strings, and allocator copies made when a `String` grows, are outside this control.

### 9. Quick unlock
Unchanged in substance: the `quick_unlock` setting (default `false`, `#[serde(default)]`, so existing configuration files keep loading) must be true for a soft lock to retain the key and for `quick_unlock` to run the polkit check; otherwise a soft lock is a hard lock, now including the session anchor and failure count. The caller check of section 3 now also applies to `quick_unlock`.

### 10. Lock hook and runtime directory
The lock hook embeds the helper path as one single-quoted shell word, with embedded `'` written as `'\''`; a test runs the generated script with a helper path containing spaces, quotes, `$HOME` and backticks. The runtime directory is `XDG_RUNTIME_DIR` only: unset, relative, a symlink, not a directory, foreign-owned or not mode `0700` is a clear error. There is no `/tmp` fallback.

### 11. Clipboard on lock
A lock (hard or soft, including suspend and an exhausted budget) never clears the clipboard. Every supervised offer the daemon serves (each `copy_field`, and each sensitive `copy` with an auto-clear) is recorded while its foreground `wl-copy` runs; the lock sends that process `SIGTERM` if it is still the same process (PID and start time), which withdraws exactly that offer, the same rule the auto-clear uses. `wl-copy` exits by itself when another application takes the selection, so text copied elsewhere after the engine's copy is left alone. A non-sensitive copy without an auto-clear (usernames, URIs) is not withdrawn.

### 12. KDF parameters of an API-key login
The KDF values an API-key login takes from the initial sync profile (when the token response omits them) are converted with a range check instead of `as u32`, which truncated larger server values, and the parameters about to be stored go through the same bounds check as prelogin and unlock. A refused value fails the login and removes the credentials already written to the keyring; nothing is saved.

## Alternatives Considered
- **Session token for the overlay** (ADR 0010, revoked): any token a same-user process can read is no barrier, and tokens in the environment break Zero-Environ.
- **Rate limiting instead of redaction**: still hands out entire items, and the first request is a full dump.
- **Making processes dumpable so the executable check always works**: weakens ADR 0009 for every user to strengthen a check that `LD_PRELOAD` bypasses anyway.
- **Polling PrepareForSleep faster**: still races the suspend; only an inhibitor makes logind wait.

## Consequences
- **Positive**: no request returns more than one secret; bulk access is bounded and self-defeating, also when paced; ordinary programs cannot use the socket; suspend waits for the lock; the daemon ends with the session; plaintext and keys are scrubbed on every path out.
- **Breaking for the overlay**: the overlay reads `login.password`, `card.number`, `notes` and similar from `vault list` today and copies by sending plaintext. It must move to the redacted shape and to `vault reveal` / `vault copy-field` (contracts.md 3.6). The QML is adapted in a following change.
- **Breaking for scripts**: `vault list`/`search` output no longer contains secrets; use `vault reveal`. Search no longer finds text inside notes. A daemon and CLI from two different installations (for example the plugin's bundled binary and `/usr/bin/omawarden`) refuse each other; use one binary.
- **Trade-off**: the executable check does not stop a determined same-user attacker (section 3); the budget and redaction are what bound such an attacker's reach through the socket.
- **Trade-off**: releasing and copying secrets no longer keeps the vault unlocked. A user who only copies passwords from the overlay, without searching, is locked after the idle interval and unlocks again.
- **Versioning**: the engine that implements this ADR is 0.12.0; the overlay requires at least that version.
